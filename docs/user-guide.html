Sentinel v2

通用主题舆情雷达 · 不锁特定行业 · 4 个独立 service · 3 端入口 · Mac launchd 自动化

v1 已完整归档至 ~/sentinel-legacy/ 和 KB _archive/v1/，不再触发。

核心特点

  • 跨行业可扩展：topic 上 industry 字段是分组标签（VPN / 教育 / 电商 …），不锁特定业务
  • 4 个独立 service：collect / alert / analyze ★ / advisor，互不阻塞、按 topic 独立开关
  • 3 个入口：Web UI（推荐）/ CLI / Skill 对话，调同一套底层
  • 主题主导信源：用户加信源时面对的是 topic，不是 collector kind
  • Topic 级告警开关：topic.alert_enabled 字段，按主题独立控制
  • 反向校验 8 字段：深度报告每议题含 ❓反例 / 🧪证伪 / ⚠️误判 / 🔗多源

3 分钟跑通

1. 装依赖

cd ~/sentinel-v2
.venv/bin/pip install -e ".[dev]"

2. 配密钥

cp secrets/.env.example secrets/.env
chmod 600 secrets/.env
# 编辑填入：TELEGRAM_API_ID/HASH/BOT_TOKEN/CHAT_ID
# 如有 SOCIALDATA_API_KEY 也填

3. 开 Web UI

.venv/bin/python -m sentinel web

浏览器打开 http://localhost:8080。在 /sources 加信源、/topics 加主题。

4. 立即手动跑一次 collect / alert

.venv/bin/python -m sentinel collect run --force
.venv/bin/python -m sentinel alert run --force [--dry-run-push]

5. 跑深度报告（人工触发）

.venv/bin/python -m sentinel analyze report --topic "X" --period 7d

6. launchd 自动化（让 v2 真接管 6h 周期）

.venv/bin/python -m sentinel deploy install     # 渲染 6 plist + launchctl load
.venv/bin/python -m sentinel deploy status      # 看部署状态
.venv/bin/python -m sentinel deploy uninstall   # 解除

4 个 service

四个独立可单跑、互不阻塞、按 topic 独立开关：

collect
launchd 02/08/14/20
遍历 enabled sources · 调 collector 拉数据 · 写 messages 入 SQLite · 不调 LLM
alert
launchd 02:30/08:30/...
从 SQLite 读新 messages → Haiku triage 三关 gate → Telegram push + KB 02-告警归档/
★ analyze
人工触发 / 周日 22:00
从 SQLite 读 → Opus 4.7 出深度报告 · 每议题 8 子标题含 4 反向校验
advisor
人工触发
读 messages + alerts + user_label · Haiku 出"加权/关闭/关键词"建议 · 覆盖式更新 03-主题/[topic]/信源.md

关键设计

  • 独立 entry：每个 service 一个 launchd plist（collect/alert/weekly/backup/watchdog 触发型 5 个 + web 长驻 1 个 = 6 个）
  • 独立 pause：.pause-collect / .pause-alert 文件，互不影响
  • 共享 runtime.shell：pause 检查 / 阈值守门 / caffeinate / run 记录 / 致命错 push / retention 全在外壳里，业务核心不写
  • 共享存储：SQLite + KB markdown 文件系统

3 个入口

所有操作都能在 Web / CLI / Skill 三端完成，底层调同一套 service Python lib。

入口何时用典型场景
Web UI 推荐 浏览历史 / 加信源 / 看运维状态 / 标记告警 python -m sentinel web → localhost:8080
CLI 脚本化 · 一次性命令 · launchd 内 python -m sentinel {collect,alert,analyze,advisor,deploy,migrate-v1,web,status}
Skill Claude Code 对话里自然语言触发 "/sentinel" / "跑下 X 周报" / "出 X 信源建议"

Skill 一览

v2 整套系统只有 1 个 skill（vs v1 的 5 个 skill）。aihot 原则 #1：SKILL.md 不堆业务逻辑，所以一个翻译层就够。

Skill触发做啥Guide
sentinel /sentinel · "舆情" · "跑下 X 周报" · "出 X 信源建议" · "sentinel 状态" 等 把用户自然语言意图翻译成 ~/sentinel-v2/ 的 CLI 命令；首选引导用户走 Web UI 做写入操作；不主动跑 LLM 类命令（除非用户明确"现在跑"） 本页 §Skill 触发词 ↓
关键设计差异 vs v1：v1 有 5 个 skill（router + config/analyze/status/daemon-ctl），v2 把所有"做事"动作搬到 Web UI 和 CLI，skill 只剩翻译层。 所以 v2 没有"router 路由到 4 个 spoke"的调用图。日常写入 / 配置 / 运维操作直接用 Web UI 更高效。

典型工作流

新加主题：从零开始监控某个话题
  1. 开 /topics
  2. 填表："name=letsvpn / industry=VPN / monitor_direction=letsvpn 自身可用性 + 主要竞品 / alert_enabled=✓"
  3. 点 topic 进详情页 /topics/{id}
  4. 关联信源（从已有 source 下拉选）
  5. 加关键词（chip 形式，逐个加）
  6. 点 "出深度报告" 立即跑一次 analyze 验证
加新信源
  1. 开 /sources
  2. 选 kind（rss / telegram / twitter / reddit / social）
  3. 填 identifier（URL / @channel / username）
  4. 默认会调 collector.resolve() 验证（telegram 需 .env 配 TG API ID/HASH）
  5. 如果是 social：identifier 填 v2ex 或 v2ex/搜索词
标记 alert 准 / 误报

/alerts 页每条 alert 旁有"标记"按钮，点开后选 ⭐ 准 / 🚫 误报 / 清。

反馈数据会进 advisor 的"反馈窗口"参与建议生成（30 天滚动）。

CLI 命令参考

所有命令默认 cd ~/sentinel-v2 && .venv/bin/python -m sentinel ...

service 操作

# 跑一次
sentinel collect run [--force]
sentinel alert run [--force] [--dry-run-push]
sentinel analyze report --topic "X" --period 7d [--mode auto|single|timeseries]
sentinel analyze weekly                          # 所有 alert_enabled topic 跑 7d 周报
sentinel advisor scan --topic "X" [--window-days 30]

# 暂停/恢复
sentinel collect pause [--days N]  # N 天后自动恢复；不填永久
sentinel collect resume
sentinel alert pause / resume

# 状态查询
sentinel status [--service collect|alert|analyze|advisor]

部署

sentinel deploy install      # 渲染 6 plist + launchctl load + 写 .host
sentinel deploy status       # 看部署状态 + host check
sentinel deploy uninstall    # unload + 移除 plist

数据迁移

sentinel migrate-v1            # dry-run · 看会从 ~/sentinel-legacy 导入什么
sentinel migrate-v1 --apply    # 实际写入
sentinel migrate-v1 --v1-db    # 指定其他 v1 db

Web UI

sentinel web [--host 127.0.0.1] [--port 8080] [--reload]

--period 时间窗格式

  • 24h · 24 小时
  • 168h 或 7d · 7 天
  • 720h 或 30d · 30 天

Skill 触发词（Claude 对话入口）

v2 1 个 skill（~/.claude/skills/sentinel/SKILL.md），只翻译意图调 CLI，不堆业务逻辑（aihot 原则 #1）。

你对 Claude 说Skill 给出的 CLI
"sentinel 状态" / "/sentinel status"sentinel status
"跑下 X 7 天周报"sentinel analyze report --topic "X" --period 7d
"出个 X 信源建议" / "/sentinel advisor X"sentinel advisor scan --topic "X"
"现在跑一次 collect"sentinel collect run --force
"暂停 collect"sentinel collect pause
"开 web UI"sentinel web
设计纪律：Skill 不主动跑会花钱的命令（analyze / advisor 都调 LLM）。除非你明确说"现在跑"，否则只把命令显示出来让你自己跑。

不该走 Skill 的场景

  • 加信源 / 加主题：让 Skill 引导你走 Web UI（有表单校验 + 即时反馈）
  • 复杂数据查询："哪些 source 信噪比最低"之类的去 Web UI /sources / /status
  • 改 service 行为：改的是 ~/sentinel-v2/sentinel/services/<svc>.py，不是 SKILL.md

Skill 入口调试

  • 触发不上：说话太抽象（"看下数据"/"舆情很乱"）→ skill 不激活。改用明确触发词，或在对话开头加 /sentinel 强制激活
  • 触发上了但翻译错：看 ~/.claude/skills/sentinel/SKILL.md 触发词 → CLI 映射表；缺映射直接编辑加（aihot 原则 #1：SKILL.md 只翻译，不写业务）
  • 升级：v2 是私有项目，没 npx 包。升级 = 改 ~/.claude/skills/sentinel/SKILL.md（编辑后下次对话生效）
  • 卸载：mv ~/.claude/skills/sentinel ~/.claude/skills/_archive/sentinel-v2-removed/。卸载后 Web UI / CLI 仍可用，只失去 Claude 对话入口
  • 路径硬编码：SKILL.md 默认 ~/sentinel-v2/。改项目位置时同步搜替换 + 改 sentinel/config.py 的 PROJECT_ROOT

# → 渲染 6 个 plist 模板（替换 PYTHON_PATH / SENTINEL_HOME / HOME）

多机感知（host check）

.host 文件机制：deploy install 时把本机 scutil --get LocalHostName 写到 ~/.kb/.../00-系统设计/.host。 副机执行 service 时 runtime.shell 检测本机 hostname ≠ .host 内容 → 友好退出，不污染主机 service_runs。

调度时段错开

alert 比 collect 滞后 30 分钟，确保 collect 完成后 alert 才判定。collect 用 StartCalendarInterval 4 时段（02/08/14/20）而非 StartInterval，因为 macOS 睡眠期间 StartInterval 不补跑。

备份与故障

SQLite 备份

scripts/backup.sh 每天 23:30 自动跑（launchd backup plist），把 db/messages.db 用 sqlite3 .backup + gzip 保存到 KB：

~/.kb/.../Sentinel/_archive/backups/messages-YYYY-MM-DD.db.gz

保留 14 天滚动。

Watchdog 监控

每天 09:00 跑 scripts/watchdog.sh：检查 collect 上次成功距今多少小时，>36h 即 Telegram push 警告。

常见故障

collect 一直 skipped — gap < threshold

正常行为：12h 阈值守门。立即跑用 --force 跳过阈值（仍尊重 pause）。

alert push 全 failed

看 ~/sentinel-v2/logs/alert.err.log。常见原因：

  • secrets/.env 没填 TELEGRAM_BOT_TOKEN / TELEGRAM_CHAT_ID
  • TG bot token 过期
  • chat_id 错误（必须是 bot 能 push 到的 chat）
analyze cluster timeout / 退到 single

>2k 消息聚类可能超时（claude CLI cli_timeout 默认 600s）。fallback 到 single mode 仍保 8 字段（v2 改进）。如果常超时可：

  • config.yaml 加大 llm.cli_timeout
  • 用更小 period（如 --period 24h）
副机调用 service 报 host mismatch

预期行为。host check 保护多机一致性。要切换部署主机：

  1. 新主机：sentinel deploy install（覆盖 .host）
  2. 旧主机：sentinel deploy uninstall
service_runs 全 failed · 看具体日志 
tail -100 ~/sentinel-v2/logs/collect.err.log
tail -100 ~/sentinel-v2/logs/alert.err.log
tail -100 ~/sentinel-v2/logs/weekly.err.log

# 或 web UI 看 /status

系统级 FAQ

跨 service / 系统层面的问题（单 skill FAQ 答不了的）：

v1 5 个 skill 都去哪了？为啥 v2 只有 1 个？
v2 是 service 化重构。v1 的 router/config/analyze/status/daemon-ctl 5 skill 主要做"路由 + UI"，v2 直接用 Web UI（含完整后台 + 运维）取代了 4 个 spoke 的 skill。sentinel 1 skill 只做"AI 翻译意图为 CLI"（aihot 原则 #1）。日常加 source / 标记 alert / 跑深度报告这些写入操作走 Web UI 比 skill 高效得多。
4 service 不会互相阻塞吗？
不会。4 个独立 launchd plist，调度时段错开（collect 整点，alert 30 分），共享只是 SQLite + KB 文件系统。collect 失败不影响 alert（alert 看上次的 messages 即可），任一 service 单独 pause/resume 也不影响其他。
跨行业怎么用？industry 字段干嘛的？
每个 topic 加一个 industry 字段（"VPN" / "教育" / "电商" / …）。industry 是轻量分组标签，没单独实体表（用 SELECT DISTINCT 派生）。Web UI /topics 按 industry 分组显示。同时 advisor / alert / analyze 的 LLM prompt 把 industry 当上下文写入，让 LLM 不锁特定行业。
从主机切到另一台 Mac 部署怎么搞？
  1. 旧主机：sentinel deploy uninstall
  2. 新主机：git clone（如已 push）或拷 ~/sentinel-v2/ 整个目录
  3. 新主机：配 secrets/.env + config.yaml
  4. 新主机：sentinel deploy install → 覆盖 .host 标识新主机
  5. 从旧 DB 迁数据：sentinel migrate-v1 --v1-db <旧主机 db 路径> --apply
v1 数据归档后还能回去查吗？
可以。v1 代码 + DB 在 ~/sentinel-legacy/（已 .pause 永久暂停）；v1 报告 / 告警归档 / 设计文档全在 02-Work/1-Pixl/Projects/Sentinel/_archive/v1/。SQLite 用 sqlite3 ~/sentinel-legacy/db/messages.db 直接查。
Telegram session 怎么共享 / 迁移？

LLM 调用花钱吗？怎么控？

怎么看哪些 source 在浪费 LLM 配额？
跑 sentinel advisor scan --topic X。它会列每个 source 的"总消息 / 命中告警 / 信噪比 / 失败数"，明确说哪些建议关闭。建议每 2-4 周跑一次。
